# Zybo Z7-10 FPGA GUI-free Demos

A modular, beginner-friendly FPGA project for the **Digilent Zybo Z7-10** board.

The goal is to learn digital design hands-on, starting from a blinking LED and building up to real-time audio processing and a full **PS + PL SoC design** (bare-metal code on the ARM cores talking to custom hardware). The one rule throughout: **no IDE, no GUI clicking** — Vivado runs in batch mode, block designs are generated by Tcl scripts, and Vitis is driven by Python. Every step is a text file you can read, diff, and reproduce.

## Getting Started

1. Clone this repository.
2. Connect the Zybo Z7-10 to your computer via the **PROG/UART** micro-USB port.
3. Set the board power switch to **USB** if you are powering from USB.
4. Run the first build:

```bash
make build TOP=top_hello
```

5. Program the FPGA:

```bash
make prog
```

6. Observe the LEDs. If the build succeeded, you should see the expected LED behavior for the current phase.

> The first build may take a few minutes because Vivado is synthesizing and implementing the design. Later builds are faster if you only change HDL.

### Trying the SoC Demo (Phase 9)

The PS + PL flow is three commands — still no GUI:

```bash
make build_soc SOC_TOP=top_ps_hello   # block design + bitstream + XSA (Vivado batch Tcl)
make app                              # compile the bare-metal C app (Vitis Python API)
make run_soc                          # program PL, run the app, print over UART (xsct)
```

Open a serial terminal on the board's USB-UART (115200 baud) and press BTN0 to see the hello message.

## Why the Command Line?

The Zybo Z7-10 contains a Zynq-7000 chip, which has two parts:

| Part | Name | What it is |
|------|------|------------|
| PS   | Processing System | A dual-core ARM Cortex-A9 CPU (like a small Linux-capable computer) |
| PL   | Programmable Logic | The FPGA fabric where we write HDL |

Most Zynq tutorials are built around GUI clicking: drag a Zynq block onto a block diagram in Vivado, click "Generate", then export to the Vitis IDE and click through more wizards. The steps live in screenshots, break between tool versions, and are impossible to diff or reproduce.

This project takes the opposite approach. **Everything is a script:**

- Vivado runs in **batch mode** driven by Tcl (`vivado -mode batch -source ...`).
- Even the SoC block design — Zynq PS, GPIO, clocks, resets — is generated entirely by `scripts/build_soc.tcl`. No block diagram is ever drawn by hand.
- The Vitis application is built by a **Python script** using the Vitis Python API — no IDE project files.
- Programming and running on hardware happens through `xsct` scripts over JTAG.

The result: you learn what the tools are actually doing, every step is version-controlled text, and the whole flow reproduces on a fresh machine.

> **Analogy:** The PS is like a Raspberry Pi sitting next to the FPGA. Phases 0–8 program only the FPGA fabric; from Phase 9 onward we boot the ARM side too — still without ever opening a GUI.

## Board Overview: Zybo Z7-10

Key features we will use:

| Resource | Count | Notes |
|----------|-------|-------|
| Slide switches (SW) | 4 | `SW0`–`SW3`, connected to FPGA pins |
| Push buttons (BTN) | 4 | `BTN0`–`BTN3`, also connected to FPGA pins |
| LEDs (single-color) | 4 | `LD0`–`LD3`, standard LEDs |
| RGB LEDs | 4 | Each has Red, Green, and Blue channels (so 12 FPGA outputs total) |
| System clock | 125 MHz | Single-ended oscillator on the board |

### Important: Active-Low vs. Active-High

On the Zybo Z7-10:

- **Buttons and switches** are active-high when pressed/on.
- **LEDs** turn on when driven **high** (`1`).
- Always double-check the board reference manual; some boards use active-low LEDs.

## Repository Structure

```
zybo_z7_fpga/
├── rtl/
│   ├── pkg/              # Shared SystemVerilog packages
│   │   └── board_pkg.sv  # Board constants (clock freq, widths, etc.)
│   ├── common/           # Reusable building blocks
│   │   ├── debounce.sv
│   │   ├── edge_detect.sv
│   │   ├── pwm.sv
│   │   └── ...
│   ├── top/              # One top-level per learning stage
│   │   ├── top_hello.sv
│   │   ├── top_button_led.sv
│   │   └── ...
│   └── tb/               # Testbenches
├── constraints/
│   ├── zybo_z7_10.xdc    # Shared board pin mapping and timing
│   └── top_*.xdc         # Per-top constraint files
├── scripts/
│   ├── build.tcl         # Vivado non-project build flow (pure PL designs)
│   ├── build_soc.tcl     # Vivado batch script: generates the PS+PL block design
│   ├── program.tcl       # Program the FPGA via JTAG
│   ├── run_soc.tcl       # Program PL + download/run the PS app (xsct)
│   └── sim.tcl           # Run simulation
├── vitis/                # Bare-metal PS applications (Phase 9+)
│   └── ps_hello/         # C source + Python build script (Vitis, no IDE)
├── build/                # Generated artifacts (ignored by git)
├── Makefile              # Convenience commands
└── README.md             # This file
```

### Directories

| Directory | Purpose |
|-----------|---------|
| `rtl/` | **Register Transfer Level** code — this is your HDL. The name is historical; think of it as "the actual digital logic." |
| `rtl/pkg/` | Packages are like shared header files in C. They hold constants and types used by many modules. |
| `rtl/common/` | Small, reusable blocks. Once written, we reuse them instead of copy-pasting code. |
| `rtl/top/` | The top-level design for each stage. This is what gets synthesized into the FPGA. |
| `rtl/tb/` | Testbenches. These are HDL files used only in simulation, not on hardware. |
| `constraints/` | Tells Vivado which FPGA pin connects to which signal and how fast the clock is. |
| `scripts/` | Tcl scripts that control Vivado from the command line — including `build_soc.tcl`, which generates the whole PS+PL block design without the GUI. |
| `vitis/` | Bare-metal C applications for the ARM PS, each with a Python build script for the Vitis command-line flow. |
| `build/` | Output files: bitstreams, reports, logs, Vitis workspace. Regenerated every build. |

## Toolchain & Workflow

We use **AMD Vivado** for synthesis, implementation, and bitstream generation, and **AMD Vitis** for the bare-metal PS applications. Both are driven entirely from the command line.

### Do I Need an IDE or GUI?

**No.** Every step — including the SoC work — can be run from the command line:

| Step | Command |
|------|---------|
| Build bitstream (pure PL design) | `make build TOP=<top_module>` |
| Program board | `make prog` |
| Run simulation | `make sim TB=<testbench>` |
| Clean artifacts | `make clean` |

From Phase 9 onward there are also **SoC targets** that include the ARM PS:

| Step | Command |
|------|---------|
| Build PS+PL block design, bitstream, and XSA | `make build_soc SOC_TOP=<soc_top>` |
| Build the bare-metal PS application (Vitis) | `make app` |
| Program PL and run the PS app via JTAG | `make run_soc` |

Under the hood:

- `make build` runs Vivado in **batch mode** (`vivado -mode batch -source scripts/build.tcl`).
- `make build_soc` runs `scripts/build_soc.tcl`, which **generates the entire block design** (Zynq PS, GPIO, clocks, resets) from Tcl — the same design a tutorial would have you draw by hand.
- `make app` invokes the **Vitis Python API** (`vitis -s vitis/ps_hello/build_app.py`) to create the platform, compile the C app, and produce the ELF — no IDE workspace files.
- `make run_soc` uses **xsct** (`scripts/run_soc.tcl`) to program the PL and download/run the ELF over JTAG.

The Vivado GUI is still useful for two things we deliberately skip:

- Viewing the synthesized schematic.
- Using the **Integrated Logic Analyzer (ILA)** to debug signals on hardware.

### Command-Line Workflow

Vivado can run in **batch mode**, meaning it executes a Tcl script without opening a window:

```bash
vivado -mode batch -source scripts/build.tcl
```

Our `Makefile` wraps these commands so you do not need to remember them.

> **What is Tcl?** Tcl (pronounced "tickle") is a scripting language. Vivado reads Tcl commands. We use it to tell Vivado: "read these files, synthesize this top module, place and route, generate a bitstream."

## Modules

The project is built in small, self-contained phases. Each phase adds one new concept and produces a working bitstream.

| Phase | Name | Concept | Top Module |
|-------|------|---------|------------|
| 0 | Hello LED | Toolchain + blinking LED | `top_hello` |
| 1 | Button-Controlled LED | Synchronization, debounce, edge detection | `top_button_led` |
| 2 | PWM RGB LED | Pulse-width modulation, parameters | `top_pwm_rgb` |
| 3 | Switch Modes | Multiplexers, pattern generators | `top_switch_modes` |
| 4 | UART Loopback | Serial communication | `top_uart_loopback` |
| 5 | FIFO | On-chip buffering and flow control | `top_fifo_loopback` |
| 6 | I2C Master | Configure the on-board audio codec | `top_i2c_codec_probe` |
| 7 | I2S Controller | Digital audio streaming | `top_i2s_tone` |
| 8 | Audio Loopback / Tone | I2C + I2S together: mic-in → headphones or generated tone | `top_audio_loopback` |
| 9 | PS Hello | First use of the ARM PS: bare-metal app, EMIO GPIO, UART | `top_ps_hello` |
| 10 | Audio Effects | BRAM delay line, saturation, bit manipulation | `top_audio_fx` |
| 11 | PS Audio Effects | PS I2C codec config, AXI GPIO control, UART menu | `top_audio_fx_soc` |

Each phase has:

- A top-level module in `rtl/top/`
- Reusable common blocks added to `rtl/common/`
- A companion `.md` doc next to each source file explaining the theory, code, and how to test it

## How to Read the Educational Material

Every module has a companion `.md` file next to its source (e.g. `rtl/common/debounce.md` for `rtl/common/debounce.sv`) with these sections:

1. **Goal** — What this module does.
2. **Concepts** — The digital-design ideas you will learn.
3. **Block Diagram** — How the pieces connect.
4. **Code Walkthrough** — Line-by-line explanation of new syntax.
5. **Parameters** — How to configure the module.
6. **Usage Example** — How to instantiate it in a top-level design.
7. **Testing** — How to simulate and run on hardware.
8. **Exercises** — Optional challenges to deepen understanding.

> **For beginners:** Do not rush. Read the code, run the simulation, load the bitstream, and observe the hardware. Change one thing at a time and see what happens.

## Prerequisites

1. **Hardware**
   - Digilent Zybo Z7-10 board.
   - Micro-USB cable for JTAG programming and power.

2. **Software**
   - AMD Vivado + Vitis (developed with **2025.2**; the unified Vitis install includes both).
   - Digilent board files installed so Vivado knows the Zybo Z7-10 (needed for the scripted block design in Phase 9; see `rtl/top/top_ps_hello.md`).
   - A text editor (VS Code, Vim, Emacs, etc.).
   - `make` (usually available on Linux/macOS; on Windows use WSL or Git Bash).

3. **Knowledge**
   - Basic digital logic: AND, OR, NOT, flip-flops, clocks.
   - Some programming experience is helpful but not required.
